# 02 K8s 架构与核心概念(知识笔记)

## 一、总体架构

### 1.1 分层全图
```
              ┌────────────────── 控制平面 (Control Plane) ──────────────────┐
 kubectl ───► │  kube-apiserver ◄──────► etcd(唯一状态存储)                   │
 客户端       │      ▲      ▲                                                   │
              │      │      └─── kube-controller-manager(几十个控制器)        │
              │      └────────── kube-scheduler(为无主 Pod 选节点)            │
              └───────────────────────┬───────────────────────────────────────┘
                                      │  list-watch(订阅) / 上报(写回)
     ┌────────────────────────────────┼────────────────────────────────┐
     │ Node 1                         │ Node 2                          │
     │  kubelet ──► containerd ──► 容器│  kubelet ──► containerd ──► 容器 │
     │  kube-proxy(Service 转发规则)  │  kube-proxy                     │
     │  [Pod][Pod]                    │  [Pod]                          │
     └────────────────────────────────┴─────────────────────────────────┘
```

### 1.2 控制面与节点的职责边界
| | 控制面 | 节点 |
|---|--------|------|
| 关心的事 | "应该是什么"(决策、状态) | "实际是什么"(执行、上报) |
| 失效影响 | 无法增删改、无自愈;**已运行 Pod 继续跑** | 该节点 Pod 失联,控制器会在别处重建(若控制器可用) |
| 扩展方式 | apiserver 无状态可横向扩;etcd 奇数扩容 | 加机器即加节点 |

- 关键推论:控制面挂 ≠ 业务挂。业务连续性依赖的是节点上的 kubelet/containerd,这决定了"控制面可以短暂不可用"的运维容忍度

### 1.3 一次请求的完整路径
```
kubectl → (认证) → (授权 RBAC) → (准入: mutating → validating) → apiserver 写 etcd
                                → (watch 到变更的组件开始行动)
```
- 认证:证书 / Token / ServiceAccount / OIDC 等,确定"我是谁"
- 授权:几乎全场景是 RBAC,确定"我能对这个资源做什么动词"
- 准入:对对象做"改"(如注入默认字段)与"验"(如 PodSecurity/Quota),在落库**之前**
- 所以 apiserver 是唯一入口:任何组件都不直连 etcd

## 二、声明式 API 与调谐循环(核心心智模型)

### 2.1 期望状态 vs 实际状态
- 每个对象由两半组成:**spec**(用户声明的期望,如 replicas: 3)+ **status**(系统回填的实际,如 readyReplicas: 2)
- 用户从不直接操作"实际",只修改"期望";把期望变成实际是系统的工作
- 这带来三个性质:**幂等**(同一声明重复提交结果相同)、**可 diff**(文件 vs 集群)、**自愈**(实际偏离期望就被纠正)

### 2.2 Reconcile(调谐)循环
控制器的心跳伪代码:
```
for {
    desired := 读取对象的 spec         // 期望
    actual   := 观测真实世界           // 实际(数 Pod、查节点…)
    if actual != desired {
        执行动作使 actual 趋近 desired  // 建Pod/删Pod/写 status
    }
}
```
- 要点1:**不记录"发生了什么事件"**,每次都重新对齐最终态 → 天然幂等,漏掉一次循环也不会错
- 要点2:失败要重试(动作可能失败,下一轮再试)
- 要点3:控制器之间通过 apiserver 解耦,互相只看对方维护的对象状态(如 Deployment 控制器只管 RS,RS 控制器只管 Pod)

### 2.3 list-watch 与 Informer(组件间通信的基石)
- 控制器不轮询 apiserver,而是:
  1. **list**:一次性拉全量对象(建立本地缓存)
  2. **watch**:订阅后续变更流(增/改/删事件实时推送)
- 客户端缓存 = **Informer**:读操作走本地缓存(不打 apiserver),写操作才发请求 → 大幅降低 apiserver 压力
- 变更流带 **resourceVersion**(全局单调递增版本号):断线重连时从上次版本续传,不丢事件
- 这个机制是"分布式系统以状态为中心协作"的典范,也是第 18 章自研控制器要直接使用的

### 2.4 声明式 vs 命令式(为什么 K8s 选声明式)
| 维度 | 命令式 | 声明式 |
|------|--------|--------|
| 表达 | "帮我执行 X" | "终态应是 Y" |
| 重复执行 | 出错或叠加副作用 | 幂等收敛 |
| 故障恢复 | 需人工补执行 | 控制器自动补齐 |
| 协作/审计 | 难(动作不留痕) | 声明即文档,可 diff/版本化 |
| 代价 | 简单直接 | 学习曲线、黑盒感("谁改了我的对象") |

## 三、控制面组件详解

### 3.1 kube-apiserver
- **唯一入口**:kubectl、dashboard、控制器、kubelet 全部只和它说话
- 自身**无状态**(不存数据,状态全在 etcd)→ 可多副本 + 前置 LB 水平扩展
- 职责链条:协议处理(TLS)→ 认证 → 授权 → 准入(变更→验证)→ schema 校验 → 序列化写 etcd → 广播 watch 事件
- 对外 API 即 REST 资源模型:`GET /api/v1/namespaces/{ns}/pods/{name}`——kubectl 只是这个 REST 的封装(`kubectl get --raw` 可直接探)
- 聚合层:把 `/apis/<组>/<版本>` 的请求按 APIService 登记分派给本地 handler 或代理给外部 Service(见 5.5)

### 3.2 etcd
- 分布式强一致 KV(Raft 共识 + MVCC 多版本)
- **集群状态的唯一存储**:所有对象、所有事件、所有配置都在里面;etcd 丢失 = 集群"失忆"
- key 布局(目录式前缀):
  ```
  /registry/pods/<ns>/<pod名>
  /registry/deployments/<ns>/<名>
  /registry/services/specs/<ns>/<名>
  /registry/apiregistration.k8s.io/apiservices/<名>
  /registry/minions/<节点名>          ← Node 对象的历史别名
  ```
  ——用 etcdctl 列 key 能直观看到"一切皆对象"
- MVCC 与 watch:每次修改产生新 revision;watch 按 revision 增量推送 → Informer 机制的地基
- quorum:奇数成员、多数派写;失去多数派 = 只读
- 运维要点:定期 `snapshot save` 备份;etcd 磁盘 IO 是集群性能敏感点

### 3.3 kube-scheduler
- 输入:尚未绑定节点的 Pod(`spec.nodeName` 为空);输出:把 nodeName 写上(绑定动作)
- **两阶段决策**:
  1. **过滤(Predicates)**——淘汰不可行节点:资源不足(requests 放不下)、端口冲突、亲和/反亲和不满足、污点不容忍、卷拓扑限制(如 RWO 卷已在别的节点)
  2. **打分(Priorities)**——对可行节点排序:资源均衡度(避免挤爆)、镜像已存在(启动快)、亲和性权重、拓扑打散得分…
- **只调度一次**语义:绑定后不再迁移;节点后续异常由控制器在别处**重建** Pod,而非搬运——所以字段名都带 `DuringSchedulingIgnoredDuringExecution`
- 纯逻辑组件:不碰容器、不碰网络,只写一个字段

### 3.4 kube-controller-manager
- 一进程内嵌几十个控制器,核心清单:
  | 控制器 | 维护的"期望→实际" |
  |--------|-------------------|
  | Deployment | Pod 模板版本 → 期望的 ReplicaSet 结构 |
  | ReplicaSet | spec.replicas → 实际存活 Pod 数 |
  | StatefulSet | 有序副本 + 标识稳定 |
  | Node | 节点心跳超时 → 标记 NotReady、驱逐计时 |
  | EndpointSlice | Service selector → 实际后端 Pod IP 列表 |
  | Job/CronJob | 任务完成数/调度 |
  | GarbageCollection | 父对象删除 → 级联清理子对象 |
- 每个控制器 = 一个(或多个)Informer + WorkQueue + Reconcile(与第 18 章自研控制器同构)
- 多副本部署时靠**Leader Election**保证同一时刻只有一个实例干活(避免双写)

## 四、节点组件详解

### 4.1 kubelet
- 节点上的"Pod 管家",职责:
  1. 注册 Node 对象并定期上报状态(容量、压力、版本)
  2. 监听指派给本节点的 Pod,驱动容器运行时按 PodSpec 创建/销毁容器
  3. 执行探针(liveness/readiness/startup 都是 kubelet 在探测)
  4. 挂载卷(configMap/secret/PVC → 容器路径)
  5. 上报 Pod 状态与事件;执行 preStop 等生命周期钩子
- 与 apiserver 的身份:节点证书 + **TLS Bootstrap**(join 时先用低权限 token 换取正式证书)
- **静态 Pod**:kubelet 直接监视本节点 `/etc/kubernetes/manifests/` 目录下的清单运行 Pod,不经过 apiserver——控制面四大件就是这样启动的("K8s 组件自己也是 Pod"的原因)

### 4.2 kube-proxy
- 使命:让 Service 的 VIP 在每个节点上"真实可用"
- **iptables 模式**(默认):为每个 Service 生成 iptables 规则链:
  ```
  目的地址=Service VIP:port → (随机概率) DNAT 到某个健康 Pod IP:targetPort
  ```
  - 规则随 Endpoints 变化由 kube-proxy 增删;转发在内核态,不经过任何用户态进程
  - 缺点:规则数 = Service×Pod 量级,大规模下规则匹配变慢(线性)
- **ipvs 模式**:用内核 IPVS(NAT 负载均衡器),哈希查找,O(1);支持 rr/lc 等多种调度算法;大规模集群首选
- 共同点:都只是"每节点一份的转发规则",没有中心代理进程;VIP 本身不属于任何网卡,只存在于规则里(所以 ping VIP 不通是**设计行为**)

### 4.3 容器运行时与 CRI
- 运行时 = 真正操作容器生命周期的软件(containerd、CRI-O;dockershim 已移除)
- **CRI(Container Runtime Interface)**:kubelet 与运行时之间的 gRPC 接口标准 → 解耦,双方可独立升级替换
- CNI(Container Network Interface)则是另一条接口:Pod 网络由 CNI 插件(kindnet/Calico/Flannel)负责——kubelet 调 CNI 给 Pod 配网卡/IP,调 CRI 起容器

## 五、资源对象模型

### 5.1 对象通用结构
```yaml
apiVersion: apps/v1     # 组/版本 → 到哪套 API 找 kind
kind: Deployment        # 类型
metadata:               # 元数据(身份与标注)
  name / namespace      # 定位:ns 级对象全 ns 唯一
  uid                   # 全局唯一 ID,重建同对象也会换
  resourceVersion      # etcd 版本号,乐观并发控制(更新需带上)
  generation            # spec 修改代数(观察滚动更新的触发)
  labels                # 标签:可筛选的键值(调度/选择器的核心)
  annotations           # 注解:不可筛选的附加信息(如 last-applied-configuration)
spec: {}                # 期望状态(用户写)
status: {}              # 实际状态(控制器回填;经 /status 子资源写)
```
- labels vs annotations 的本质区别:**labels 用于"选"(selector 语法),annotations 用于"存"**(工具元数据、原始配置)

### 5.1.1 实例:第一个 Pod(lab02-first-pod.yaml 注解)
```yaml
apiVersion: v1                  # 核心组,无组名
kind: Pod                       # 最小调度单元
metadata:
  name: web                     # Pod 名,ns 内唯一
  namespace: dev                # 归属命名空间(不写=default)
  labels:
    app: web                    # 标签:第 08 章 Service 靠它选 Pod
spec:
  containers:
    - name: nginx               # 容器名,同 Pod 内唯一
      image: nginx:1.27         # 仓库/名称:tag
      ports:
        - containerPort: 80     # 声明性信息:不写也能访问
      resources:
        requests: { cpu: 50m, memory: 64Mi }   # 调度预留(只有 requests,无 limits → Burstable)
```
- 该文件无控制器字段 → 裸 Pod,删了没人重建(与第 05 章 Deployment 的对比点)

### 5.2 API 组与版本
- **核心组(legacy)**:组名为空 → apiVersion 直接写 `v1`;含 Pod/Service/ConfigMap/Secret/Namespace/PV/Event
- **命名组**:`apps`(工作负载)、`batch`(任务)、`networking.k8s.io`、`rbac.authorization.k8s.io`、`storage.k8s.io`、`autoscaling`、`policy`…
- 版本:alpha(实验)→ beta(默认关)→ stable;同一资源可多版本并存,apiserver 负责转换
- 版本优先级由 APIService 的 versionPriority 决定(你查过的那个字段)

### 5.3 资源分类总览
| 类别 | 对象 | 关键词 |
|------|------|--------|
| 工作负载 | Pod/ReplicaSet/Deployment/StatefulSet/DaemonSet/Job/CronJob | 副本、模板、控制器 |
| 服务发现 | Service/Ingress/EndpointSlice | 稳定入口、路由 |
| 配置 | ConfigMap/Secret | 配置与代码分离 |
| 存储 | Volume/PV/PVC/StorageClass | 供给与解耦 |
| 安全 | SA/Role/Binding/SecurityContext | 身份与权限 |
| 治理 | ResourceQuota/LimitRange/HPA | 配额与弹性 |
| 扩展 | CRD/Operator | 自定义资源与控制器 |

### 5.4 作用域:集群级 vs 命名空间级
- ns 级:绝大多数(业务对象)
- 集群级:Node、PV、StorageClass、Namespace 本身、ClusterRole、APIService、CRD
- 判断意义:名字唯一性范围、RBAC 授权粒度、配额管理范围

### 5.5 APIService 与 API 聚合(机制还原)
- APIService = "某 API 组/版本由谁提供"的登记条目,**纯声明对象、无进程**
- 三种服务方式:
  1. **Local**:内置组,apiserver 自己服务(status reason=Local,永远可用)
  2. **Service 代理**:spec.service 指向某 Service(如 metrics-server)→ apiserver 把该组的请求**反向代理**过去(这就是"聚合层")
  3. **CRD**:CRD 控制器注册的组,同样由 apiserver 直接服务(不产生带 service 的 APIService)
- 用 `kubectl get apiservices` 看到的清单 = 集群全部 API 能力的注册表;安装扩展(metrics-server、Prometheus Operator)后清单会变长
- 实例(集群里真实存在的登记条目,内容精简):
```yaml
apiVersion: apiregistration.k8s.io/v1
kind: APIService
metadata:
  name: v1.apps                              # 名 = <版本>.<组>(核心组为 v1.)
  labels:
    kube-aggregator.kubernetes.io/automanaged: onstart   # apiserver 启动时自动注册
spec:
  groupPriorityMinimum: 18000                # 组在 API 发现中的排序优先级
  version: v1
  versionPriority: 1                         # 同组内多版本排序
status:
  conditions:
    - type: Available
      status: "True"
      reason: Local                          # Local = apiserver 自己服务,永远可用
      message: Local APIServices are always available
```

### 5.6 对象间的关联手段
| 手段 | 用途 | 例子 |
|------|------|------|
| 标签+选择器 | 松耦合圈选(selector) | Service 选 Pod、Deployment 选 Pod |
| ownerReferences | 父子归属(级联删除) | RS→Pod、Deployment→RS |
| 命名约定 | 弱关联 | PVC 与 PV 的 claimRef |
| 资源引用字段 | 显式指向 | spec.serviceName、claimName |

## 六、Namespace

### 6.1 它隔离什么、不隔离什么
| 隔离 ✅ | 不隔离 ❌ |
|--------|-----------|
| 对象命名空间(名字冲突) | 网络(ns 间默认互通) |
| 权限边界(RBAC 按授权) | 节点资源(共享调度) |
| 配额(ResourceQuota/LimitRange) | Pod IP(全局平面) |
| 默认网络策略作用域 | 镜像/StorageClass(集群级共享) |

- 本质:**软隔离/管理边界**,不是安全边界;硬隔离靠多集群

### 6.1.1 实例:创建 Namespace(lab01-namespace.yaml 注解)
```yaml
apiVersion: v1
kind: Namespace               # 集群级对象:名字全集群唯一
metadata:
  name: dev                   # 分区名
  labels:
    env: dev                  # 标签:后续配额/RBAC/策略按 env 圈选
---
# --- 是 YAML 文档分隔符:一个文件装多个对象
apiVersion: v1
kind: Namespace
metadata:
  name: test
  labels:
    env: test
---
# 第三段结构相同,prod 同理
```
- 无 spec:Namespace 没有期望状态可写,本身就是"分区"这个事实

### 6.2 内置命名空间
| ns | 内容 |
|----|------|
| default | 未指定 ns 的落点 |
| kube-system | 组件与 addon(apiserver/etcd/Coredns/kube-proxy) |
| kube-public | 公开可读信息(如 cluster-info) |
| kube-node-lease | 节点心跳 Lease 对象(轻量、高频) |
| (kind 特有)local-path-storage | 默认存储供给器 |

## 七、静态 Pod

### 7.1 原理
- kubelet 直接监视本节点 `/etc/kubernetes/manifests/*.yaml` 运行 Pod:文件出现→创建,修改→重建,删除→移除
- 完全绕过 apiserver: apiserver 里能**看到**这些 Pod(只读镜像,由 kubelet 反向同步),但不能通过 apiserver 控制

### 7.2 与普通 Pod 的差异
| 维度 | 普通 Pod | 静态 Pod |
|------|----------|----------|
| 来源 | apiserver(控制器创建) | 节点本地文件 |
| 控制器管理 | ✅ | ❌(kubelet 直接管) |
| apiserver 可删/改 | ✅ | ❌(改文件才生效) |
| 典型用途 | 业务 | 控制面组件(kube-apiserver/etcd/scheduler/controller-manager) |

- 设计动机:鸡生蛋问题——apiserver 自己还没起来时,谁来拉起 apiserver?答案:每个节点的 kubelet + 本地清单

## 八、机制串联:一次 Deployment 创建的完整链路(复习)

```
1. kubectl apply → apiserver(认证/授权/准入)→ etcd 落库 Deployment
2. Deployment 控制器 watch 到新对象 → 按模板创建 ReplicaSet(写 etcd)
3. RS 控制器 watch 到 RS → 按 replicas 创建 N 个 Pod(无 nodeName)
4. scheduler watch 到无主 Pod → 过滤+打分 → 写入 nodeName
5. 对应节点 kubelet watch 到"分给我的 Pod" → 调 CRI 拉镜像起容器、调 CNI 配网络
6. kubelet 上报 Pod 状态 → EndpointSlice 控制器把就绪 Pod IP 写入后端列表
7. kube-proxy 在各节点更新转发规则 → Service 流量可达
```
- 每一步都是"某组件 watch 自己关心的对象 → 调谐 → 写回"——整张架构图就是 2.2 那个循环的分工实现
