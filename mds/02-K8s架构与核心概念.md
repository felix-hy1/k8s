## 2.1 整体架构图

```
                        ┌─────────────────── 控制面 (Control Plane) ───────────────────┐
   kubectl /客户端 ───► │  kube-apiserver ◄──► etcd (集群所有状态的唯一存储)           │
                        │       ▲    ▲                                                   │
                        │       │    └── kube-controller-manager (副本/节点/端点等控制器)│
                        │       └─────── kube-scheduler (为无主 Pod 选择节点)           │
                        └───────────────────────────┬───────────────────────────────────┘
                                                    │ (监听 + 上报)
        ┌───────────────────────────────────────────┼───────────────────────────────────┐
        │                节点 Node 1                 │              节点 Node 2          │
        │  kubelet ──► 容器运行时(containerd)       │  kubelet ──► containerd          │
        │  kube-proxy(维护 Service 的 iptables 规则) │  kube-proxy                      │
        │  [Pod] [Pod] [Pod]                         │  [Pod] [Pod]                     │
        └────────────────────────────────────────────┴──────────────────────────────────┘
```

**核心心智模型**:你(用户)只向 apiserver **声明期望状态**(比如"我要 3 个 nginx"),控制器们不断**对比期望与实际**并自动纠偏(Reconcile 循环)。这就是"声明式 API"。

## 2.2 控制面组件

| 组件 | 作用 | 类比 |
|------|------|------|
| kube-apiserver | 唯一入口,所有读写都经过它;认证/鉴权/准入 | 前台总服务台 |
| etcd | 分布式 KV 数据库,保存全部对象数据 | 档案库 |
| kube-scheduler | 只做一件事:给未调度的 Pod 挑节点 | 分诊台 |
| kube-controller-manager | 副本控制器、节点控制器、Deployment 控制器等集合 | 各科室自动巡检员 |

## 2.3 节点组件

| 组件 | 作用 |
|------|------|
| kubelet | 节点代理,按 PodSpec 保证容器按期望运行(健康检查、日志、挂载卷) |
| kube-proxy | 在每个节点维护 Service 的 VIP → Pod 的转发规则(iptables/ipvs) |
| 容器运行时 | 真正跑容器的软件(containerd/CRI-O),通过 CRI 接口与 kubelet 交互 |

## 2.4 资源对象全景(后面各章逐一展开)

| 类别 | 对象 | 对应章节 |
|------|------|----------|
| 工作负载 | Pod, ReplicaSet, Deployment, StatefulSet, DaemonSet, Job, CronJob | 04~07 |
| 服务发现 | Service, Ingress, EndpointSlice | 08~09 |
| 配置 | ConfigMap, Secret | 10 |
| 存储 | Volume, PV, PVC, StorageClass | 11 |
| 安全 | ServiceAccount, Role, RoleBinding, SecurityContext | 14 |
| 策略/扩展 | ResourceQuota, HPA, CRD, Operator | 15/18 |

**对象通用结构**:`apiVersion`(组/版本)→ `kind`(类型)→ `metadata`(name/namespace/labels)→ `spec`(期望状态)→ `status`(实际状态,系统填写)。

## 2.5 Namespace

- 集群内的"虚拟集群",用于隔离资源与权限边界
- 内置:`default`(默认)、`kube-system`(组件)、`kube-public`、`kube-node-lease`
- 跨 Namespace 的对象:Node、PV、StorageClass、ClusterRole 等(集群级)

## 2.6 YAML 清单详解:每个字段是什么意思

**任何** K8s 资源的 YAML 都是同一个骨架,先背下这五段,再看任何清单都不会懵:

```yaml
apiVersion: v1          # ① 用哪套 API(组/版本)—— 决定"去哪张表里登记"
kind: Pod               # ② 资源类型 —— 决定"登记什么"
metadata:               # ③ 元数据 —— 这对象叫什么、贴什么标签(不含业务逻辑)
  name: web
  namespace: dev
  labels: { app: web }
spec:                   # ④ 期望状态 —— 你写,告诉集群"我要它长什么样"
  containers: [ ... ]
status:                 # ⑤ 实际状态 —— 系统写,你永远不用手写
  phase: Running
```

**记忆法**:`metadata` 管"身份",`spec` 管"我要什么",`status` 管"实际怎样"(控制器对比 spec 和 status 不一致就自动纠偏——这就是声明式的实现)。

### 2.6.1 五个顶层字段逐个讲

| 字段 | 必填? | 含义 | 常见值 |
|------|-------|------|--------|
| `apiVersion` | ✅ | API 组/版本。核心对象组为空(`v1`),其他对象是"组/版本" | `v1`(Pod/Service/ConfigMap/NS)、`apps/v1`(Deployment/StatefulSet/DaemonSet)、`batch/v1`(Job/CronJob)、`networking.k8s.io/v1`(Ingress/NetworkPolicy)、`autoscaling/v2`(HPA)、`rbac.authorization.k8s.io/v1`(RBAC) |
| `kind` | ✅ | 资源类型(首字母大写的单数名) | Pod、Service、Deployment… |
| `metadata` | ✅ | 元数据:名字、命名空间、标签、注解 | 见 2.6.2 |
| `spec` | 多数✅ | **期望状态**,每种资源结构不同,是各章详解的主体 | — |
| `status` | ❌ | **实际状态,系统维护**。手写会被忽略/覆盖;`kubectl get -o yaml` 里看到的才是它 | — |

> 一个文件里可以写多个对象,用 `---` 分隔(本手册所有 lab 都是这么组织的)。

### 2.6.2 metadata 详解:身份四件套

```yaml
metadata:
  name: web              # 名字。同类型+同 ns 内唯一;小写字母数字和 '-',≤253 字符
  namespace: dev         # 属于哪个分区;不写 = default(Node/PV 等集群级对象不能写)
  labels:                # 标签:键值对,可写多个,给"机器筛选"用
    app: web
    version: v2
    env: prod
  annotations:           # 注解:给"人和工具"读的备注,不能被 selector 引用
    description: "订单系统前端"
```

**labels(标签)**:纯元数据,不影响运行行为,但 K8s 里一大半机制都靠它工作——

- Service 的 `selector` 按标签找 Pod(第 08 章)
- Deployment 的 `selector.matchLabels` 绑定它管的 Pod 模板(第 05 章)
- 节点打标签 + `nodeSelector`/亲和性,控制 Pod 落点(第 12 章)
- 命令行筛选:`kubectl get pods -l app=web`、`-l 'env in (prod,staging)'`

键值规范:键 ≤63 字符(前缀如 `app.kubernetes.io/name` 除外),值 ≤63 字符。**数量不限**,按"维度"命名即可:`app`(是什么)、`version`(哪版)、`env`(什么环境)、`tier`(哪一层)、`team`(谁维护)。

**labels vs annotations 对比**:

| | labels | annotations |
|---|---|---|
| 给谁用 | 机器筛选(selector、调度、命令行) | 人和工具读(说明、变更记录) |
| 值的形态 | 简短键值(≤63 字符) | 长文本、甚至结构化数据 |
| 能被 selector 引用 | ✅ | ❌ |

判断标准:**要用来"选"对象的写 labels,只是"备注"的写 annotations**。

### 2.6.3 完整示例:逐行注释版

用本章实验的 `lab02-first-pod.yaml` 逐行解读(做完实验 4 回来看):

```yaml
apiVersion: v1                # Pod 属于核心 API 组,版本 v1
kind: Pod
metadata:
  name: web                   # Pod 名(之后 kubectl 都用它指代)
  namespace: dev              # 落在 dev 分区(实验 1 建的)
  labels:
    app: web                  # 将来 Service 靠这个标签找到它
spec:                         # ↓ 期望状态:这个 Pod 里跑什么
  containers:                 # 容器列表(Pod 可以有多个,见第 04 章)
    - name: nginx             # 容器名(Pod 内唯一)
      image: nginx:1.27       # 镜像:仓库/名字:标签。务必固定 tag,别用 latest
      ports:
        - containerPort: 80   # 声明性信息:容器监听 80(纯文档作用,不写也通)
      resources:
        requests:             # 申请量:调度时按这个"占坑"(第 15 章细讲)
          cpu: 50m            # 50m = 0.05 核
          memory: 64Mi        # Mi = 2^20 字节
```

### 2.6.4 遇到没见过的字段怎么查(授人以渔)

```bash
# ① 这个集群有哪些资源类型?
kubectl api-resources                    # KIND 列就是可以写的 kind,APIVERSION 列就是 apiVersion

# ② 逐层查字段文档(最常用!)
kubectl explain pod
kubectl explain pod.spec
kubectl explain pod.spec.containers.resources

# ③ 看一个活对象的完整结构(含 status):
kubectl get pod web -n dev -o yaml

# ④ 官方 API 参考(最权威,搜 kind 名):
#    https://kubernetes.io/docs/reference/kubernetes-api/
```

**各字段的深度详解在后续章节**:Pod 全字段(探针/钩子/QoS)→ 第 04 章;Deployment 策略 → 第 05 章;Service 端口三兄弟(port/targetPort/nodePort)→ 第 08 章。本章掌握"骨架 + 查询方法"即可。

## 常见问题

| 问题 | 答案 |
|------|------|
| 控制面挂了业务还能跑吗? | 能。已运行的 Pod 不受影响,但无法新增/变更/自愈 |
| etcd 备份怎么做? | `etcdctl snapshot save`,生产必备 |
| kind 的节点里还有一层容器? | 是,kubelet 把节点容器当宿主机,里面再跑容器(sibling 模式) |
