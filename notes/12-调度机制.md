# 12 调度机制(知识笔记)

> 约定:YAML 示例出自 `~/k8s-lab/12-调度机制/manifests/lab01~lab04`,编号与章节对应。

## 一、调度器原理

### 1.1 两阶段模型:过滤 → 打分 → 绑定
```
Pod 创建(无 nodeName)
   ▼
① Predicates 过滤(硬淘汰,答"能不能去")
   资源够不够(requests vs 节点可分配)/ 端口冲突 / nodeSelector·亲和性不满足 /
   污点不容忍 / volume 拓扑限制(如 local PV 钉死节点)/ taint NoExecute 已驱逐
   ▼ 剩下可行节点集
② Priority 打分(软排序,答"最想去哪")
   资源均衡度(避免挤爆一台)/ 镜像已在本节点(省拉取)/ preferred 亲和性权重 / 拓扑打散倾向
   ▼ 最高分节点
③ Bind 绑定:把 nodeName 写进 PodSpec,kubelet 接手创建容器
```
- 过滤是**布尔**淘汰,打分是**加权**排序——所有"软偏好"都活在这一层
- 排错入口:Pod 卡 Pending 时 `describe pod` 尾部 Events 会**逐条列出被过滤的原因**(0/3 nodes are available: 2 node(s) didn't match..., 1 node(s) had untolerated taint...)

### 1.2 只调度一次(Ignored 的一半含义)
- 调度是**一次性判决**:绑定后哪怕条件恶化(标签被改、节点资源被占),已运行 Pod **不会被主动迁移**
- 全部亲和性字段名都叫 `...DuringSchedulingIgnoredDuringExecution`——直译"只在调度时算,执行期装看不见",名字即机制
- 推论:Deployment 扩容时新 Pod 按新局面选址,**旧 Pod 原地不动**;想重排要删 Pod 重建或上 Descheduler

### 1.3 控制手段全景:谁在说话
| 手段 | 站在谁那边 | 语义 | 强弱 |
|------|-----------|------|------|
| nodeSelector | Pod | 只去带某标签的节点 | 硬 |
| nodeAffinity required | Pod | 必须满足的节点条件 | 硬 |
| nodeAffinity preferred | Pod | 加权偏好 | 软 |
| podAffinity | Pod | 贴着某类 Pod 同域 | 硬或软 |
| podAntiAffinity | Pod | 离某类 Pod 远点(不同域) | 硬或软 |
| topologySpreadConstraints | Pod | 按拓扑域均匀铺开(maxSkew) | 硬或软 |
| **taints + tolerations** | **节点** | 节点驱离默认 Pod,带容忍者豁免 | 节点侧控制 |

- 前 6 行是 **Pod 拉式**(我想去哪),最后一行是**节点推式**(我赶走谁)——两组正交,可叠加
- Pod 侧手段写在 `spec.affinity` / `spec.nodeSelector` / `spec.topologySpreadConstraints`;节点侧污点是节点的属性,容忍写在 Pod 的 `spec.tolerations`

### 1.4 与旧知识的接口
| 旧知识 | 在调度器里的角色 |
|--------|------------------|
| resources.requests(04 章) | 过滤阶段的资源标尺——requests 是调度筹码,limits 不是 |
| 第 07 章 DaemonSet 的两行 tolerations | 本章污点机制的预演:不容忍 control-plane 污点就铺不满 3 节点 |
| 第 11 章 local-path PV 的 nodeAffinity | 过滤条件之一"volume 拓扑":货品钉死在哪个节点,Pod 只能跟过去 |
| QoS(04 章) | 不影响"去哪",影响"节点紧张时谁被驱逐"(驱逐≠调度) |

## 二、节点维度:nodeSelector 与 nodeAffinity

### 2.1 nodeSelector:最简硬匹配
```yaml
spec:
  nodeSelector:
    disktype: ssd        # 节点必须带 disktype=ssd 标签;没有 → Pending
  containers:
    - { name: app, image: nginx:1.27 }
```
- 语法就是**节点标签的等值匹配**,一行搞定
- 局限:只能"等于",没有"尽量"、没有多选一——这些能力全在 nodeAffinity 里
- 前置动作是给节点贴标签(`kubectl label node <n> disktype=ssd`),标签是整个调度体系的地基

### 2.2 节点亲和性:软硬两级 + 运算符(完整注解)
```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:   # 硬:过滤阶段生效
        nodeSelectorTerms:              # 多个 term 之间是 OR(任一满足即可)
          - matchExpressions:
              - key: disktype           # 看节点的哪个标签
                operator: In            # 属于集合
                values: [ssd, nvme]     # ssd 或 nvme 都行(nodeSelector 做不到)
      preferredDuringSchedulingIgnoredDuringExecution:  # 软:打分阶段加权
        - weight: 80                    # 权重 1~100,参与打分排序
          preference:
            matchExpressions:
              - { key: disktype, operator: In, values: [nvme] }   # 更爱 nvme
        - weight: 20
          preference:
            matchExpressions:
              - { key: disktype, operator: In, values: [ssd] }    # 其次 ssd
  containers:
    - { name: app, image: nginx:1.27 }
```
- **required 和 preferred 可以并存**:硬条件圈定候选(ssd/nvme 二选一),软偏好在候选里挑最好的(有 nvme 绝不去 ssd)
- `nodeSelectorTerms` 内多个 term 是 **OR**;同一个 term 内多条 matchExpressions 是 **AND**——组合逻辑的关键细节
- 软偏好不保证结果:候选里只有 ssd 时,nvme 偏好落空也照样调度(落到 ssd)

### 2.3 运算符家族
| operator | 语义 | 示例 |
|----------|------|------|
| In | 值属于集合 | disktype In [ssd,nvme] |
| NotIn | 不属于(注意:会连"没有该标签的节点"也算满足) | 同上取反 |
| Exists | 标签键存在(不看值) | key 存在即可 |
| DoesNotExist | 标签键不存在 | 排除带某标签的节点 |
| Gt / Lt | 数值比较(标签值须是数字) | cpu-core Gt 8 |

### 2.4 无节点可满足 → Pending(排错观察对象)
```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - { key: disktype, operator: In, values: [nvme] }   # 集群里没有 nvme 节点
  containers:
    - { name: app, image: nginx:1.27 }
```
- 结果:Pod **永远 Pending**——硬条件没人满足,调度器不妥协
- describe 的 Events 原文类似:`0/3 nodes are available: 2 node(s) didn't match Pod's node affinity/selector, 1 node(s) had untolerated taint ...`——**这段话就是过滤器的验尸报告**,逐条对应被淘汰原因
- 呼应第 11 章:引用了 Pending PVC 的 Pod 同样 Pending,两类 Pending 要区分看(卷没就绪 vs 调度不动)

## 三、Pod 维度:亲和与反亲和

### 3.1 podAffinity:贴着某类 Pod 跑
```yaml
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels: { app: cache }           # 找带这个标签的 Pod(别的 Deployment 的)
          topologyKey: kubernetes.io/hostname     # 拓扑域 = 同一节点
  containers:
    - { name: web, image: nginx:1.27 }
```
- 语义:web 必须和"至少一个 cache Pod"**落在同一个拓扑域**——低延迟访问缓存的经典布局
- **topologyKey 是域的定义**:`kubernetes.io/hostname`(每节点一域)= "同节点";换成 `topology.kubernetes.io/zone` 就是"同可用区"——同一个字段,把"贴多近"变成可调参数
- 被依赖方(cache)不需要任何配置——亲和是单方面声明

### 3.2 podAntiAffinity:离某类 Pod 远点
```yaml
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels: { app: spread-web }      # 注意:选的是自己这类 Pod
          topologyKey: kubernetes.io/hostname     # 每节点一域
  containers:
    - name: web
      image: nginx:1.27
      resources:
        requests: { cpu: 20m, memory: 32Mi }
```
- 语义:任何节点上只要有 spread-web 的 Pod,就不能再放新的 spread-web——**每节点最多 1 副本**,高可用布局(一台挂了还有俩)
- labelSelector 选自己(模板里的 labels)是固定套路:Deployment 的每个副本互相排斥
- 前提:3 副本恰好 3 节点才调度得开(见 3.3)

### 3.3 自锁陷阱:required 反亲和 × 副本数 > 节点数
```
3 节点 + replicas: 3 → 恰好每节点 1 个 ✓
replicas 扩到 4   → 第 4 个 Pod:每个节点都已有同类 → 全部被过滤 → 永久 Pending ✗
```
- 硬反亲和把"分散"写成了铁律,容量天花板 = 节点数;扩容即自锁,且**已运行的 3 个不会被挪走**(1.2 的 Ignored 机制)
- 生产解法:preferred 反亲和(软分散,挤不下就将就)+ PDB(15 章,保至少几个可用);或用拓扑打散(第五节)替代

## 四、节点侧控制:污点与容忍

### 4.1 语义:与亲和性方向相反
- 亲和性是 **Pod 拉式**:"我想去"
- 污点是**节点推式**:"默认谁都别来,带豁免权的除外"——适合"这台机器专用于某团队/某用途"的场景
- 污点是节点的**属性**(`kubectl taint` 打上去),容忍写在 Pod 里——一对配合:节点立规矩,Pod 出示通行证

### 4.2 taint 命令与三种 effect
```bash
kubectl taint node k8s-learning-worker2 team=ml:NoSchedule   # 打污点:key=value:effect
kubectl taint node k8s-learning-worker2 team=ml:NoSchedule-   # 删除:结尾加减号(高频忘)
```
| effect | 对新 Pod | 对已有 Pod |
|--------|----------|------------|
| NoSchedule | 不调度 | 不动 |
| PreferNoSchedule | 尽量不调度(软) | 不动 |
| **NoExecute** | 不调度 | **驱逐**不容忍者 |

- `NoSchedule` 是最常用档;`NoExecute` 是唯一能赶走存量 Pod 的(驱逐机制,区别于调度)
- 污点三元组 = key + value + effect,**容忍时三者都要对上**(或用 Exists 通配)

### 4.3 tolerations 语法(完整注解)
```yaml
spec:
  tolerations:
    - key: "team"              # 污点的 key
      operator: "Equal"        # Equal:精确匹配 value;Exists:只要 key 在(不看值)
      value: "ml"
      effect: "NoSchedule"     # 对应污点的 effect;不写 = 容忍该 key 的所有 effect
  containers:
    - { name: app, image: nginx:1.27 }
```
- `Equal` 模式:key+value+effect 三对齐才算容忍成功
- 宽松变体:
  | 写法 | 含义 | 风险 |
  |------|------|------|
  | `operator: Exists`(无 key) | 容忍**一切污点** | 生产勿用,等于自带万能通行证 |
  | 有 key + Exists | 容忍该 key 的任意 value | 适度放宽 |
  | 不写 effect | 容忍该 key 全部 effect | 常见省略 |
- NoExecute 场景可加 `tolerationSeconds: 300`:被驱逐前最多赖 300 秒(默认系统 Pod 常配 300s)

### 4.4 实例闭环:控制面为什么只跑系统 Pod
- kind/K8s 默认给控制面打 `node-role.kubernetes.io/control-plane:NoSchedule`(1.24 前叫 `.../master`,所以第 07 章 DaemonSet 清单里两行容忍就是新旧 key 各一条)
- kube-system 的系统 Pod(kube-proxy/apiserver 等)**清单里自带对应容忍**——所以它们能上控制面,业务 Pod 不能
- 这解释了此前多个章节"Pod 从不落控制面"的现象:不是 ROLES 列的魔法,是一条污点在过滤

## 五、拓扑打散 topologySpreadConstraints

### 5.1 为什么不用反亲和
- required 反亲和的"每域最多 1 个"太死:副本数超节点数就自锁(3.3)
- 拓扑打散的模型更合理:**控制不均衡度**(maxSkew),而不是"每域只准一个"——副本再多也只是尽量摊匀

### 5.2 完整配置注解
```yaml
spec:
  topologySpreadConstraints:
    - maxSkew: 1                                  # 任意两域副本数差 ≤ 1(不均衡上限)
      topologyKey: kubernetes.io/hostname         # 拓扑域:节点级(生产常用 zone 级)
      whenUnsatisfiable: DoNotSchedule            # 摊不开就 Pending;ScheduleAnyway = 软约束
      labelSelector:
        matchLabels: { app: balanced }            # 统计"我自己这类"在各域的数量
  containers:
    - name: web
      image: nginx:1.27
      resources:
        requests: { cpu: 20m, memory: 32Mi }
```
- 打分视角:调度器数一遍"app=balanced 目前在各节点各有几个",把新副本放进**最少的域**(补短板)

### 5.3 maxSkew 的算法直观(4 副本 3 节点)
```
第 1 个 → 随便(0/0/0 → 1/0/0)
第 2 个 → 最少域(1/0/0 → 1/1/0)
第 3 个 → 最少域(1/1/0 → 1/1/1)
第 4 个 → 都并列最少,打分挑一个(→ 2/1/1)   maxSkew=1 全程满足
第 5 个 → 任何落点都造成 2/1/2? 不,→ 2/2/1   仍满足;但第 6 个前若 3/2/1 再来 → Pending
```
- 若 `whenUnsatisfiable: ScheduleAnyway`:摊不开也不挡,只是降权尽量匀——**生产推荐软档**,兼顾高可用与可调度性

## 六、运维动作:cordon / drain / uncordon

```bash
kubectl cordon k8s-learning-worker      # 禁止新 Pod 调度 → STATUS 出现 SchedulingDisabled
kubectl drain k8s-learning-worker \
  --ignore-daemonsets \                 # DaemonSet 每节点必须有,驱了又会被补,跳过
  --delete-emptydir-data                # emptyDir 数据随 Pod 死,需显式授权才肯驱
kubectl uncordon k8s-learning-worker    # 恢复可调度
```
- 三者关系:cordon 是"关门"(新客不进);drain 是"清场+关门"(存量 Pod 驱逐重建到别处,隐含 cordon);uncordon 开门
- drain 的实现底牌:给节点打 `node.kubernetes.io/unschedulable:NoSchedule` 污点 + 逐个驱逐(eviction API,走优雅终止,与直接 delete pod 的区别是经过 API 限速与 PDB 保护)
- 运维节点(升级内核/重启)**标准流程:cordon → drain → 干活 → uncordon**——不 drain 直接重启 = Pod 硬死,控制器虽会重建但用户会看到中断
- 两个参数为什么存在:DaemonSet 驱不干净(ignore)、emptyDir 里有临时数据(delete-emptydir-data),K8s 强迫你显式表态,防止误杀

## 七、选型速查(场景 → 手段)

| 需求 | 手段 | 强度 |
|------|------|------|
| 只能跑在特定规格机器 | nodeSelector / required nodeAffinity | 硬 |
| 有 SSD 更好,没有也行 | preferred nodeAffinity(weight) | 软 |
| web 贴着 cache 同节点 | podAffinity + topologyKey=hostname | 硬/软 |
| 副本尽量每节点一个 | podAntiAffinity(required 慎用)/ 拓扑打散 | 看写法 |
| 副本按机房/节点摊匀 | topologySpreadConstraints(maxSkew) | 硬或软 |
| 这台机器专用(如 ML 团队) | taint + 对应 tolerations | 节点侧 |
| 节点要维修 | cordon/drain/uncordon | 运维动作 |

- 总记忆:**Pod 拉式看 affinity 三兄弟 + spread,节点推式看 taint;软硬之分 = 过滤阶段还是打分阶段;所有规则只在调度那一刻生效,存量 Pod 永不自动迁移**
