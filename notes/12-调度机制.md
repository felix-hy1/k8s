# 12 调度机制(知识笔记)

> 约定:YAML 示例出自 `~/k8s-lab/12-调度机制/manifests/lab01~lab04`,编号与章节对应;标注【实况】的内容为实验运行的真实结果(与理想模型的差异点)。

## 一、调度器原理

### 1.1 两阶段模型:过滤 → 打分 → 绑定
```
Pod 创建(无 nodeName)
   ▼
① Predicates 过滤(硬淘汰,答"能不能去")
   资源够不够(requests vs 节点可分配)/ 端口冲突 / nodeSelector·亲和性不满足 /
   污点不容忍 / volume 拓扑限制(如 local PV 钉死节点)/ taint NoExecute 已驱逐
   ▼ 剩下可行节点集
② Priority 打分(软排序,答"最想去哪")
   资源均衡度(避免挤爆一台)/ 镜像已在本节点(省拉取)/ preferred 亲和性权重 / 拓扑打散倾向
   ▼ 最高分节点
③ Bind 绑定:把 nodeName 写进 PodSpec,kubelet 接手创建容器
```
- 过滤是**布尔**淘汰,打分是**加权**排序——所有"软偏好"都活在这一层
- 排错入口:Pod 卡 Pending 时 `describe pod` 尾部 Events 会**逐条列出每个节点被过滤的原因**,每个分句 = 一个节点 + 一条规则,逐句对号入座

### 1.2 只调度一次(Ignored 的一半含义)
- 调度是**一次性判决**:绑定后哪怕条件恶化(标签被改、节点资源被占),已运行 Pod **不会被主动迁移**
- 全部亲和性字段名都叫 `...DuringSchedulingIgnoredDuringExecution`——直译"只在调度时算,执行期装看不见",名字即机制
- 推论:Deployment 扩容时新 Pod 按新局面选址,**旧 Pod 原地不动**;想重排要删 Pod 重建或上 Descheduler

### 1.3 控制手段全景:谁在说话
| 手段 | 站在谁那边 | 语义 | 强弱 |
|------|-----------|------|------|
| nodeSelector | Pod | 只去带某标签的节点 | 硬 |
| nodeAffinity required | Pod | 必须满足的节点条件 | 硬 |
| nodeAffinity preferred | Pod | 加权偏好 | 软 |
| podAffinity | Pod | 贴着某类 Pod 同域 | 硬或软 |
| podAntiAffinity | Pod | 离某类 Pod 远点(不同域) | 硬或软 |
| topologySpreadConstraints | Pod | 按拓扑域均匀铺开(maxSkew) | 硬或软 |
| **taints + tolerations** | **节点** | 节点驱离默认 Pod,带容忍者豁免 | 节点侧控制 |

- 前 6 行是 **Pod 拉式**(我想去哪),最后一行是**节点推式**(我赶走谁)——两组正交,可叠加
- 落点公式:**通过 Pod 的硬条件 ∧ 通过节点的门禁(污点全被容忍)→ 在候选里打分取最高**,两边各杀各的,Events 常见多类死因同框

### 1.4 与旧知识的接口
| 旧知识 | 在调度器里的角色 |
|--------|------------------|
| resources.requests(04 章) | 过滤阶段的资源标尺——requests 是调度筹码,limits 不是 |
| 第 07 章 DaemonSet 的两行 tolerations | 本章污点机制的预演:不容忍 control-plane 污点就铺不满 3 节点 |
| 第 11 章 local-path PV 的 nodeAffinity | 过滤条件之一"volume 拓扑":货品钉死在哪个节点,Pod 只能跟过去 |
| QoS(04 章) | 不影响"去哪",影响"节点紧张时谁被驱逐"(驱逐≠调度) |

## 二、节点维度:nodeSelector 与 nodeAffinity

### 2.1 nodeSelector:最简硬匹配(lab01 ns-pod)
```yaml
spec:
  nodeSelector:
    disktype: ssd        # 节点必须带 disktype=ssd 标签;没有 → Pending
  containers:
    - { name: app, image: nginx:1.27 }
```
- 语法就是**节点标签的等值匹配**,一行搞定
- 局限:只能"等于",没有"尽量"、没有多选一——这些能力全在 nodeAffinity 里
- 前置动作是给节点贴标签(`kubectl label node <n> disktype=ssd`),标签是整个调度体系的地基

### 2.2 节点亲和性:软硬两级 + 运算符(lab01 affinity-pod 完整注解)
```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:   # 硬:过滤阶段生效
        nodeSelectorTerms:              # 多个 term 之间是 OR(任一满足即可)
          - matchExpressions:
              - key: disktype           # 看节点的哪个标签
                operator: In            # 属于集合
                values: [ssd, nvme]     # ssd 或 nvme 都行(nodeSelector 做不到)
      preferredDuringSchedulingIgnoredDuringExecution:  # 软:打分阶段加权
        - weight: 80                    # 权重 1~100,参与打分排序
          preference:
            matchExpressions:
              - { key: disktype, operator: In, values: [nvme] }   # 更爱 nvme
        - weight: 20
          preference:
            matchExpressions:
              - { key: disktype, operator: In, values: [ssd] }    # 其次 ssd
  containers:
    - { name: app, image: nginx:1.27 }
```
- **required 和 preferred 可以并存**:硬条件圈定候选(ssd/nvme 二选一),软偏好在候选里挑最好的(有 nvme 绝不去 ssd)
- **组合逻辑的关键细节**:`nodeSelectorTerms` 内多个 term 是 **OR**;同一个 term 内多条 matchExpressions 是 **AND**
- 软偏好不保证结果:候选里只有 ssd 时,nvme 偏好落空也照样调度
- 软偏好参与的是打分层:本集群过滤后常只剩一个候选,preferred"陪跑"——节点多了它才真正做主

### 2.3 运算符家族
| operator | 语义 | 示例 |
|----------|------|------|
| In | 值属于集合 | disktype In [ssd,nvme] |
| NotIn | 不属于(注意:会连"没有该标签的节点"也算满足) | 同上取反 |
| Exists | 标签键存在(不看值) | key 存在即可 |
| DoesNotExist | 标签键不存在 | 排除带某标签的节点 |
| Gt / Lt | 数值比较(标签值须是数字) | cpu-core Gt 8 |

### 2.4 无节点可满足 → Pending(lab01 no-fit-pod)
```yaml
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - { key: disktype, operator: In, values: [nvme] }   # 集群里没有 nvme 节点
```
- 结果:Pod **永远 Pending**——硬条件没人满足,调度器不妥协
- 【实况】describe Events 两类死因同框:`2 node(s) didn't match Pod's node affinity/selector, 1 node(s) had untolerated taint {...control-plane...}`——worker/worker2 死于亲和不匹配,控制面死于污点(它连进入亲和比对的资格都没有),污点过滤与标签过滤同在第一轮硬淘汰里,各杀各的

## 三、Pod 维度:亲和与反亲和

### 3.1 podAffinity:贴着某类 Pod 跑(lab02 with-cache)
```yaml
spec:
  affinity:
    podAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels: { app: cache }           # 找带这个标签的 Pod(别的 Deployment 的)
          topologyKey: kubernetes.io/hostname     # 拓扑域 = 同一节点
  containers:
    - { name: web, image: nginx:1.27 }
```
- 语义:必须和"至少一个 cache Pod"**落在同一个拓扑域**——低延迟访问缓存的经典布局
- **topologyKey 是域的定义**:`kubernetes.io/hostname`(每节点一域)= "同节点";`topology.kubernetes.io/zone` = "同可用区"——**"贴多近"是可调参数**
- 被依赖方(cache)不需要任何配置——亲和是**单方面声明**,前提是锚点有稳定标签
- 时序两特性(都源自"只调度一次"):①required 亲和要求域内**已存在**匹配 Pod,磁铁没起来它就 Pending 等;②磁铁后来搬走,它**原地不跟**

### 3.2 podAntiAffinity:离某类 Pod 远点(lab02 spread-web)
```yaml
spec:
  affinity:
    podAntiAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels: { app: spread-web }      # 选"自己人":副本互相排斥
          topologyKey: kubernetes.io/hostname
  containers:
    - name: web
      image: nginx:1.27
      resources:
        requests: { cpu: 20m, memory: 32Mi }      # 压到极小:让资源过滤永不抢戏,现象才纯粹
```
- 语义:节点上已有同类 Pod 就禁止再放——**每节点最多 1 副本**,高可用布局的标准写法
- labelSelector 选自己(模板标签)是固定套路:Deployment 的副本互相排斥
- 【实况】本集群 3 节点但控制面带污点 → **结局是 2 Running + 1 永久 Pending**(见 3.3)

### 3.3 自锁陷阱:required 反亲和 × 副本数 > 可用节点数(lab02 实况)
```
理想假设:3 节点 + replicas:3 → 每节点 1 个 ✓
真实结局:控制面被污点挡住,可用节点只有 2 个
         → 第 3 个 Pod 永久 Pending(扩容前就锁死了,还没到"扩到 4"那一步)
```
- 验尸报告:`1 node(s) had untolerated taint {...control-plane...}, 2 node(s) didn't match pod anti-affinity rules`——again 两类死因同框
- 天花板是**可用**节点数(过得了全部过滤的),不是节点总数——"节点够副本数"要打折算
- 生产解法:preferred 反亲和(软分散,挤不下就将就)+ PDB(15 章);或换拓扑打散(第五节)

## 四、节点侧控制:污点与容忍

### 4.1 语义:与亲和性方向相反
- 亲和性是 **Pod 拉式**:"我想去";污点是**节点推式**:"默认谁都别来,带豁免权的除外"
- 污点是节点的**属性**(管理员提前配好,对所有 Pod 无差别生效),容忍写在 Pod 里——节点立规矩,Pod 出示通行证

### 4.2 taint 命令与三种 effect
```bash
kubectl taint node k8s-learning-worker2 team=ml:NoSchedule   # 打污点:key=value:effect
kubectl taint node k8s-learning-worker2 team=ml:NoSchedule-   # 删除:结尾减号(高频忘)
```
| effect | 对新 Pod | 对已有 Pod |
|--------|----------|------------|
| NoSchedule | 不调度 | 不动 |
| PreferNoSchedule | 尽量不调度(软) | 不动 |
| **NoExecute** | 不调度 | **驱逐**不容忍者 |

- 污点三元组 = key + value + effect,容忍时三者都要对上(或用 Exists 通配)

### 4.3 tolerations 语法(lab03 tolerant-pod)
```yaml
spec:
  tolerations:
    - key: "team"              # 污点的 key
      operator: "Equal"        # Equal:精确匹配 value;Exists:只要 key 在(不看值)
      value: "ml"
      effect: "NoSchedule"     # 对应污点的 effect;不写 = 容忍该 key 的所有 effect
  containers:
    - { name: app, image: nginx:1.27 }
```
宽严光谱:
| 写法 | 豁免范围 | 评价 |
|------|----------|------|
| key + Equal + value + effect | **恰好一条污点** | 最严最精确,生产推荐 |
| key + Exists | 该 key 的任意 value | 适度放宽 |
| 纯 `operator: Exists`(无 key) | **一切污点** | 万能通行证,生产勿用 |
| 不写 effect | 该 key 全部 effect | 常见省略,注意同时豁免了 NoExecute |

- NoExecute 场景可加 `tolerationSeconds: 300`:被驱逐前最多赖 300 秒(优雅收尾窗口)

### 4.4 实例闭环:控制面为什么只跑系统 Pod
- kind/K8s 默认给控制面打 `node-role.kubernetes.io/control-plane:NoSchedule`(1.24 前叫 `.../master`,所以第 07 章 DaemonSet 清单里两行容忍就是新旧 key 各一条)
- kube-system 系统 Pod 清单里**自带对应容忍**——所以它们能上控制面,业务 Pod 不能

### 4.5 容忍是"许可"不是"偏好"(lab03 纠偏)
- toleration 只负责**摘掉过滤条件**,不参与打分:tolerant-pod 落 worker 或 worker2 都正常
- "专用节点"完整配方三件套:**taint(节点拦人)+ toleration(获准进)+ nodeAffinity(指名去)**——只发通行证不指路,Pod 可能走错门

### 4.6 每个 Pod 自动继承的两条容忍(describe 可见)
```
node.kubernetes.io/not-ready:NoExecute     tolerationSeconds=300
node.kubernetes.io/unreachable:NoExecute   tolerationSeconds=300
```
- 系统默认注入:节点短暂失联时 Pod 最多"赖"5 分钟再被驱逐——避免网络抖动引发全集群大逃亡
- 验证:`kubectl describe pod <任意> | grep -A4 Tolerations`(没写过 tolerations 的 Pod 也能看到这两条)

## 五、拓扑打散 topologySpreadConstraints

### 5.1 为什么不用反亲和
- required 反亲和的"每域最多 1 个"太死:副本数超**可用**节点数就自锁(3.3 实况)
- 拓扑打散的模型更合理:**控制不均衡度**(maxSkew),而不是"每域只准一个"——副本再多也只是摊匀

### 5.2 完整配置注解(lab04)
```yaml
spec:
  topologySpreadConstraints:                   # 复数:可写多条(zone 一条 + 节点一条是生产标配)
    - maxSkew: 1                               # 任意两域数量差 ≤ 1(封顶的是"差值"不是"数量")
      topologyKey: kubernetes.io/hostname      # 域 = 节点(生产高可用常用 zone)
      whenUnsatisfiable: DoNotSchedule         # 硬档:违反就出局;ScheduleAnyway = 软档只降权
      labelSelector:
        matchLabels: { app: balanced }         # 数"自己人"在各域的数量,新副本进最少的域
  containers:
    - name: web
      image: nginx:1.27
      resources:
        requests: { cpu: 20m, memory: 32Mi }   # 压到极小,让资源过滤永不抢戏
```

### 5.3 maxSkew 逐副本落位(理想态:2 个可用域)
```
worker/worker2 两域(控制面被污点排除在可落点之外):
1/0 → 1/1 → 2/1 → 2/2    4 副本全 Running
对比 lab02 互斥模型:副本数(4)超过可用域数(2)照样活——maxSkew 没有"容量天花板"
```
- `whenUnsatisfiable: ScheduleAnyway`:摊不开也不挡,只降权尽量匀——**生产推荐软档**

### 5.4 域资格的真相(lab04 踩坑实录,文档级 gotcha)
- **Pod 调不进去的域不会被"除名"**:它的现有数量(通常 0)仍参与**全局最小值**的计算
```
实况:lab03 的 team=ml 污点残留在 worker2 → 可落点只剩 worker
     全局最小 = 0(worker2/控制面的 0 也计入)
     worker 已有 1 个副本 → 再放:1+1-0 = 2 > maxSkew=1 → spread 过滤拒绝 worker
     终局:1 Running + 3 Pending(Events 解剖见第八节)
```
- 官方文档对此场景的建议:换 `ScheduleAnyway`;或恢复域数量(撤污点)
- 记忆:**污点偷走的不是"节点",是"打散的余地"**——可用域越少,maxSkew 越容易触顶
- 完整判据(过滤时):`本域现有数 + 1 − 全局最小 ≤ maxSkew` 才放行

## 六、运维动作:cordon / drain / uncordon

```bash
kubectl cordon k8s-learning-worker      # 禁止新 Pod 调度 → STATUS 出现 SchedulingDisabled
kubectl drain k8s-learning-worker \
  --ignore-daemonsets \                 # DaemonSet 每节点必须有,驱了又补,跳过
  --delete-emptydir-data                # emptyDir 数据随 Pod 死,需显式授权才肯驱
kubectl uncordon k8s-learning-worker    # 恢复可调度
```
- 三者关系:cordon 是"关门"(新客不进);drain 是"清场+关门"(存量 Pod 驱逐重建到别处,隐含 cordon);uncordon 开门
- drain 的实现底牌:给节点打 `node.kubernetes.io/unschedulable:NoSchedule` 污点 + 逐个驱逐(eviction API,走优雅终止,受 PDB 保护)——**节点的赶人策略不只静态配置,运维时也能动态上锁**
- 运维节点标准流程:**cordon → drain → 干活 → uncordon**;不 drain 直接重启 = Pod 硬死
- 两个参数为什么存在:DaemonSet 驱不干净(ignore)、emptyDir 里有临时数据(delete-emptydir-data),K8s 强迫显式表态防误杀

## 七、选型速查(场景 → 手段)

| 需求 | 手段 | 强度 |
|------|------|------|
| 只能跑在特定规格机器 | nodeSelector / required nodeAffinity | 硬 |
| 有 SSD 更好,没有也行 | preferred nodeAffinity(weight) | 软 |
| web 贴着 cache 同节点 | podAffinity + topologyKey=hostname | 硬/软 |
| 副本尽量每节点一个 | podAntiAffinity(required 慎用)/ 拓扑打散 | 看写法 |
| 副本按机房/节点摊匀 | topologySpreadConstraints(maxSkew) | 硬或软 |
| 这台机器专用(如 ML 团队) | taint + 对应 tolerations(+ nodeAffinity 指名) | 节点侧 |
| 节点要维修 | cordon/drain/uncordon | 运维动作 |

- 总记忆:**Pod 拉式看 affinity 三兄弟 + spread,节点推式看 taint;软硬之分 = 过滤阶段还是打分阶段;所有规则只在调度那一刻生效,存量 Pod 永不自动迁移**

## 八、实验排错现场:一次教科书级的 FailedScheduling(lab04 实录)

Events 原文:
```
0/3 nodes are available: 1 node(s) didn't match pod topology spread constraints,
1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: },
1 node(s) had untolerated taint {team: ml}.
preemption: 0/3 nodes are available: 1 No preemption victims found for incoming pod,
2 Preemption is not helpful for scheduling.
```

| 分句 | 对应节点 | 死于哪条规则 |
|------|----------|--------------|
| didn't match pod topology spread constraints | worker | 打散过滤:全局最小=0(不可用域也计入),worker 已 1 个,再放差值 2 > maxSkew=1 |
| untolerated taint {control-plane} | 控制面 | 污点过滤(系统自带) |
| untolerated taint {team: ml} | worker2 | 污点过滤(lab03 残留未撤销) |

- **preemption 行不是新错误**:调度器考虑"抢占低优先级 Pod 腾位"后的结论(无对象可抢/抢了无用),常规信息,读报告时跳过即可
- 修复三板斧:①撤销残留污点 `kubectl taint node k8s-learning-worker2 team=ml:NoSchedule-`(结尾减号) ②打散降软档 ScheduleAnyway ③给 Pod 补容忍
- 排错心法:**Events 每个分句 = 一个节点 + 一条过滤规则**,逐句对号入座,根因自明——本章所有 Pending 现象共用这一套读法
