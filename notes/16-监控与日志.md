# 16 监控与日志(知识笔记·开发者视角)

> 约定:YAML 示例出自 `~/k8s-lab/16-监控与日志/manifests/`(kube-prom-stack-values.yaml / lab01-log-generator.yaml / prometheus-rule-example.yaml);标注【实况】为安装与实验的真实结果。本章运维细节按开发者所需深度裁剪。

## 一、可观测性三支柱(问题的分类学)

| 支柱 | 回答的问题 | 形态 | 生态 |
|------|-----------|------|------|
| **Metrics 指标** | 系统什么状态? | 数字,可画图聚合 | Prometheus + Grafana |
| **Logging 日志** | 具体发生了什么? | 文本,有现场细节 | kubectl logs → Loki/ES |
| Tracing 链路 | 请求经过了哪里? | 调用链 | Jaeger/Tempo(本书不展开) |

- 出问题先分类:**看趋势/大盘 → Metrics;查单次现场 → Logging;跨服务追路径 → Tracing**
- 与 15 章的关系:`kubectl top` 是即时快照(不存历史、不能告警);本章是完整体系——**从"看一眼"升级到"看得住"**

## 二、Prometheus 体系(一条链路 + 四个角色)

### 2.1 架构图
```
exporter(各处暴露 /metrics 文本页) ←定时抓取(pull)─  Prometheus(时序库+规则求值)──►  Grafana(查询画图)
                                                        └─触发─►  Alertmanager(分组/静默/通知)
```
- **exporter = 报数员**:任何组件把自身指标暴露成 HTTP 文本页 `指标名{标签} 值`
  - node-exporter:节点 CPU/内存/磁盘(**DaemonSet 部署,每节点一个**——第 07 章知识一眼认亲)
  - kube-state-metrics:K8s 对象状态(Pod 重启次数等,实验 4 的数据源)
- **Prometheus = 中枢**:主动拉取、存时序库、周期求值告警规则
- **Grafana = 画图**:每条曲线背后是一条 PromQL 查询,看图 = 别人替你写好了查询
- **metrics-server vs Prometheus**:
  | | metrics-server(15 章) | Prometheus(本章) |
  |--|----------------------|------------------|
  | 定位 | 问一句答一句的快照 | 持续抄表 + 存历史 + 算告警 |
  | 服务对象 | kubectl top / HPA | 人类(大盘/告警) |
  | 存储 | 不存 | 时序库(retention 配置) |

### 2.2 kube-prometheus-stack = Helm 一条龙
- 十几个组件打包成一张 **Chart**(Helm 的包),一条 `helm install` 全装:Prometheus Operator + Prometheus 实例 + Grafana + Alertmanager + 两个 exporter + 预置仪表盘/规则
- Helm 三词(17 章正课,本章会用即可):**repo**(软件源)/ **chart**(包=模板集合)/ **release**(一次安装实例,资源名的前缀来源)
- 全家桶约 1.5GB 内存;学习环境用 values 调低配置

## 三、values 文件解读(安装时传给 chart 的参数表)

### 3.1 本质
```
chart 模板(挖好变量坑的 YAML 骨架) + values.yaml(覆盖参数) ──渲染──► 最终清单 → apply
```
- 同一张 chart 服务学习与生产:**模板不变,参数千变**;改配置 = `helm upgrade -f 新values`(17 章)

### 3.2 关键定制逐条注解
```yaml
fullnameOverride: kps            # 资源名统一 kps- 前缀(否则是 kps-kube-prometheus-stack-xxx 长蛇)
prometheus:
  prometheusSpec:                # ← 会被渲染成 Prometheus CR,由 Operator 执行(见第五节)
    retention: 2d                # 数据只留 2 天(学习省盘;生产按审计 30d/90d)
    resources:
      requests: { cpu: 200m, memory: 768Mi }
      limits: { memory: 1Gi }    # ★ 只限内存不限 CPU:CPU limit 会节流,抓取高峰被节流=丢数据
    serviceMonitorSelectorNilUsesHelmValues: false
    serviceMonitorSelector: {}   # ★ 空选择器=全选:放开认领所有 ServiceMonitor(默认只认 release=kps 标签的)
grafana:
  adminPassword: prom-operator   # 明文密码,生产必改
  service: { type: ClusterIP }   # 不开 NodePort 的洞,管理面用 port-forward 临时开门(安全惯例)
alertmanager:
  config:
    receivers: [ { name: "null" } ]   # 学习环境"静音":告警只在 UI 走流转,不真发通知
kubeStateMetrics: { enabled: true }   # 组件开关:false 即不装
nodeExporter: { enabled: true }       # 就是那 3 个 DaemonSet Pod
```
- **"CPU 不设 limit、内存设 limit"** 是性能敏感组件(Prometheus 等)的生产惯例——15 章"节流"教训的直接应用
- **空选择器 = 全选**(`serviceMonitorSelector: {}`)与 NetworkPolicy 空 podSelector、DaemonSet 认领是同一惯用法
- 注意:values 只放开了 ServiceMonitor 的认领;**PrometheusRule 仍要求 `release: kps` 标签**(实验 4 的坑)

## 四、安装实况与坑

### 4.1 安装动线
```bash
# Helm 本体(curl 官方脚本;要在配了代理的交互终端跑)
curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
# 加源 + 安装(几分钟,拉十几个镜像)
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install kps prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace -f kube-prom-stack-values.yaml
# 等就绪 + 验收(node-exporter 应每节点一个)
kubectl -n monitoring wait --for=condition=ready pod -l release=kps --timeout=600s
kubectl get pods -n monitoring
```

### 4.2 【实况】Grafana ImagePullBackOff(节点直连限流)
- 现象:全家桶里唯独 `docker.io/grafana/grafana:13.2.1-distroless` 拉不动(ImagePullBackOff)
- 根因:**节点 containerd 拉镜像是"无代理直连"**(daemon.json 代理只给宿主 dockerd,节点内 containerd 是独立通道)→ 裸连 Docker Hub 撞匿名限流;而 quay.io 的镜像都正常
- 修法三板斧(第 01 章 load-image.sh 的设计场景):
```bash
bash ~/k8s/01/scripts/load-image.sh grafana/grafana:13.2.1-distroless   # 宿主机代理拉 → 注入节点
kubectl -n monitoring delete pod <grafana-pod>                          # 重建,IfNotPresent 命中本地
```
- 一般规律:**quay.io 稳,docker.io 可能限流;撞了就"宿主代拉 + 注入"**

### 4.3 访问与排错
```bash
kubectl port-forward -n monitoring svc/kps-grafana 3000:80 --address 0.0.0.0 &
# 浏览器 localhost:3000,admin / prom-operator
kubectl port-forward -n monitoring svc/kps-kube-prometheus-stack-prometheus 9090:9090 &   # Prometheus UI
```
- Grafana 打不开九成是 port-forward 进程死了(它是前台挂着的);Dashboards → 自带预置仪表盘足够用,Import ID(315/1860/747/8588)是可选项

## 五、CRD 与 Operator(第一个自定义资源)

- `apiVersion: monitoring.coreos.com/v1`、`kind: PrometheusRule`——**原生 K8s 不认识这两个词**:装 stack 时 Operator 把新类型(CRD)**教给了 apiserver**
- 从此 `kubectl get prometheusrule` 和 `get pods` 一样自然;Operator watch 这类对象 → **翻译成 Prometheus 原生配置**——apply YAML,几秒后告警列表生效,全程没人碰配置文件
- values 里的 `prometheusSpec` 同理:渲染成 Prometheus CR,由 Operator 执行——**连 Prometheus 自己都是"声明出来的"**
- 这是 18 章(CRD/Operator)的活标本;章内涉及:PrometheusRule(告警)、ServiceMonitor(抓取对象声明)

## 六、PrometheusRule 告警解剖(实验 4 全解)

### 6.1 完整注解
```yaml
apiVersion: monitoring.coreos.com/v1   # Operator 教的新词(CRD)
kind: PrometheusRule
metadata:
  name: pod-restart-alert
  namespace: monitoring
  labels:
    release: kps        # ★ 认领标签:没有它规则不被评估("告警不生效"头号原因)
spec:
  groups:               # 规则按组组织(同组共享评估周期,默认约 30s 一次)
    - name: pod.rules
      rules:
        - alert: PodRestartTooOften                       # ① 告警名
          expr: increase(kube_pod_container_status_restarts_total[15m]) > 3   # ② PromQL
          for: 1m                                        # ③ 防抖:持续满足才转正
          labels: { severity: warning }                  # ④ 级别(路由/分组用)
          annotations:                                   # ⑤ 给人看的文案(动态模板)
            summary: "Pod {{ $labels.namespace }}/{{ $labels.pod }} 频繁重启"
            description: "15 分钟内重启 {{ $value | printf \"%.0f\" }} 次"
```

### 6.2 expr 拆解(读懂一条告警查询)
| 片段 | 含义 |
|------|------|
| `kube_pod_container_status_restarts_total` | 每容器**累计**重启次数(计数器,只增不减;kube-state-metrics 报的) |
| `[15m]` | 回看窗口 |
| `increase(...)` | 计数器在窗口内涨了多少 = 15 分钟内重启次数 |
| `> 3` | 逐序列布尔判断,命中的才产生告警 |

### 6.3 for 与三态生命周期
```
Inactive ─expr 首次为真→ Pending(候选,还在 for 期)─持续真满 1m→ Firing(正式告警,才通知)
   ↑____________________条件转假随时回落_____________________↓
```
- 没有 for,一次抖动就半夜叫醒人——**告警系统最怕狼来了**,冷静期是标配

### 6.4 annotations 模板
- `{{ $labels.pod }}` 取命中序列的标签、`{{ $value }}` 取当前值——报警文本动态填空,值班人一眼知道"哪个 Pod、几次"

## 七、日志体系(本章 Logging 半场)

### 7.1 链路:stdout 交给平台
```
应用 echo 到 stdout(应用唯一的职责)
  → 容器运行时(containerd)落盘节点 /var/log/pods/<ns>_<pod>/<容器>/0.log
  → kubectl logs 读这份文件(--previous 读轮转前的旧文件)
  → (集群级)DaemonSet 部署 Promtail/Fluent Bit 采集 → Loki/ES 集中检索
```
- 12-Factor 原则:**应用只管 stdout,建文件/轮转/清理/采集全是平台的活**——开发者 `console.log` 到 stdout 即尽责
- 落盘实证:`docker exec k8s-learning-worker ls /var/log/pods/`

### 7.2 kubectl logs 三板斧
```bash
kubectl logs -f deploy/log-app -n mon-lab --tail=100     # 实时 + 最近 100 条
kubectl logs deploy/log-app -n mon-lab --since=1h        # 时间窗
kubectl logs <pod> --previous                            # ★ 崩溃前的遗言(CrashLoop 排错第一现场)
```
- **logs 是 Pod 级的**:`logs deploy/xxx` 只是取第一个 Pod 的便利写法,多副本想全看用 **stern**(`stern -n ns 'pattern'` 多 Pod 同盯)

### 7.3 日志发生器的设计(lab01)
- `case $((i % 10))` 节奏:每 10 条 1 个 ERROR、1 个 WARN、8 个 INFO——**模拟真实应用配比**,分级检索才有得练
- `$(date)` 运行时 shell 替换;`- |` YAML 块字面量写多行脚本
- resources 极小但齐全——每个清单都写 resources 是好习惯(HPA 分母/Quota 记账/QoS)

## 八、开发者排查套路(本章真正的带走物)

### 8.1 三步定位法
```
服务慢  → top/Grafana 看 CPU 是否贴 limit(15 章节流,不报错不重启)
服务死  → RESTARTS + describe Last State(OOMKilled 137 / CrashLoopBackOff)
行为怪  → logs 翻现场(-f 实时 / --since 时间窗 / --previous 上辈子)
```

### 8.2 告警不生效三板斧
```
① 标签对没对(PrometheusRule 要带 release: kps 才被认领)
② 指标有没有数(把 expr 拿到 Prometheus Web UI 手跑一遍)
③ 是不是还在 Pending(for 期没满,不是坏了)
```

### 8.3 求助时会说的话
- "我们 ns 的 CPU/内存曲线在哪看"(Grafana 仪表盘选 namespace)
- "能不能给我们的服务加个重启/内存告警"(一条 PrometheusRule 的事)
- 知道找谁、要什么,不必自己会配
